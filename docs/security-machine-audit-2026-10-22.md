# Security audit of this workstation — 22 October 2026

**This machine has several high-priority security update gaps.** The strongest configuration-confirmed finding is a Nix daemon privilege-escalation vulnerability. The running kernel also matches upstream ranges for two vulnerabilities CISA identifies as actively exploited, plus last week's PwnEscape disclosure. Brotli, Node.js, browsers, certificate trust material, and several desktop libraries need attention.

This was a read-only assessment of `nixos-pablo`, focused on **15–22 October 2026**, Africa/Johannesburg time, with older vulnerabilities included when they remain relevant here. No exploit, build, Nix evaluation, package update, activation, service restart, or configuration change was performed. The only authored files are these research reports. **Vulnerability matches do not establish that this machine has been compromised.** Intrusion investigation was outside this audit.

See the [disclosure research and complete recent KEV additions](security-disclosures-research-2026-10-22.md) and [all 59 npm advisory matches](security-dependency-audit-2026-10-22.md).

## Why so many packages match

The active and booted system both resolve to:

`/nix/store/f0yf3i854ks02is6grq8zn15yxfccs28-nixos-system-nixos-pablo-26.11.20260616.567a49d`

The working-tree `flake.lock` also pins Nixpkgs to `567a49d1913ce81ac6e9582e3553dd90a955875f`, dated **16 June 2026**. Custom app updates have brought some applications forward while much of the shared system software remains at that snapshot. A recent application build or recent activation date therefore does not establish that its libraries are patched.

The audit enumerated **2,958 unique Nix store paths** across the active system and both user profiles. These include generated assets and multiple outputs; this is not a count of 2,958 independent packages. It queried existing store metadata only, without evaluating the flake or triggering builds. Kernel derivation patches were the Nix integration patches for STP, request-key, and randstruct; no relevant networking security backport appeared. Nix and curl had empty patch lists. OpenSSL's listed patches concerned certificate paths and kernel detection, not the September security fixes.

## Actual local exposure

- **SSH listens on `0.0.0.0:22` and `[::]:22`.** The generated configuration permits password and keyboard-interactive authentication and disallows root login. `hosts/common.nix` permits TCP 22, and the firewall service is active. Internet reachability was not tested; listening on all interfaces does not prove public exposure. Effective `sshd -T` inspection failed because the unprivileged audit cannot read host keys; no private key content was read.
- **PostgreSQL and Redis are published to host loopback only**, on `127.0.0.1:5432` and `127.0.0.1:6379`. That reduces direct remote exposure. Both share a Docker network, so other containers and local users/applications remain relevant. They are not privileged containers. Database authorization and application-mediated access were not tested.
- The Docker context points to **`unix:///var/run/docker.sock`**, confirming the container evidence comes from this host. The current account belongs to `wheel`, `docker`, `libvirtd`, and `kvm`; it already has substantial administrative access. The Nix finding still affects the boundary for other allowed users and compromised processes, but is not evidence that the current account was previously isolated from all routes to administration.
- **Tailscale** has listeners bound to its interface, including TCP 443; UDP 41641 is also bound. **dnsmasq** serves the libvirt bridge. Tailnet ACLs, the service behind Tailscale 443, router/NAT rules, and external reachability were not audited.
- Kernel settings include `CONFIG_IPV6=y`, `CONFIG_NET_NS=y`, `CONFIG_USER_NS=y`, `CONFIG_INET=y`, `CONFIG_PACKET=m`, `CONFIG_TUN=m`, `CONFIG_BRIDGE_NF_EBTABLES=m`, and `CONFIG_BRIDGE_EBT_SNAT=m`. TUN is loaded and `/dev/net/tun` exists with mode `0666`; namespace limit is **256716**. A TUN device being openable does not itself grant network-administration capabilities. These are reachability indicators, not exploit results.
- `kernel.unprivileged_bpf_disabled=2` was observed. This does not fix the independently identified Nix or networking vulnerabilities.
- Two Convex containers are stopped. Their stored images were not audited or treated as currently exposed services. Virtual-machine guest operating systems were not inspected.

## Repository dependencies: many matches, with an important reachability distinction

The OSV query checked **885 unique public npm package/version pairs** across four lockfiles. It returned **59 distinct non-withdrawn advisories** for **13 package/version pairs**: **1 critical, 17 high, 38 moderate, 3 low** by database severity. These numbers are advisory matches, not independent exploitable applications.

Five matched advisories were published during Oct 15–22: four for **`@modelcontextprotocol/sdk 1.29.0`** and one for **`hono 4.12.17`**. The SDK issues concern HTTP validation exhaustion, session-bound tasks, OAuth/redirect behavior, and bearer-token audience checks; the relevant fixed SDK release is **1.32.0**. The recent Hono static-file issue is fixed in **4.13.11**. Source links and all other matches are in the [dependency appendix](security-dependency-audit-2026-10-22.md).

Those versions are installed in the MCP bridge, but its audited entry point constructs **`StdioClientTransport`**, not an HTTP transport. Consequently the reported HTTP/server/OAuth vulnerabilities are **not demonstrated reachable through that entry point**. The critical `proxy-addr 2.0.7` database match is also installed, but its HTTP proxy-trust path was not demonstrated. These deserve dependency maintenance without being misrepresented as proven remote compromise of this bridge.

The Sanity and Pi lockfiles already had user changes before the audit; working-tree lockfile matches are not automatically the same as the installed closure. No npm lifecycle scripts were executed and no lockfiles were changed.

## What this week's headlines did not establish here

The retrieved CISA snapshot had **nine KEV additions dated Oct 15–21**, covering Atlassian, BeyondTrust, Fortinet, SiteGuard, Plex, and Siemens. Those products were not identified in the active system closure/running-service inventory. This is not a statement about external appliances, managed infrastructure, or VM guests. The full list and vendor references are in the [research report](security-disclosures-research-2026-10-22.md).

**PHP2Shell (CVE-2026-109618/109619)** is important recent news, but PHP was not identified in the active Nix closure and neither running container is a PHP application. This audit did not inspect every image layer or guest filesystem, so it does not rule out dormant PHP copies. [PHP maintainer advisory](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w).

Two other Linux KEV entries, **CVE-2025-39964** and **CVE-2025-39682**, were fixed upstream in 6.17; the observed 6.18.35 kernel is beyond those fixes. They were excluded from findings instead of reporting every Linux KEV entry as applicable.

## Recommended order of work

1. **Patch the Nix daemon and kernel first.** The Nix daemon configuration directly matches the privilege-escalation advisory, and two kernel matches have documented exploitation elsewhere. Kernel activation requires a reboot to replace the running kernel.
2. **Refresh the shared Nixpkgs base, Brotli/Node, trust stores, browsers and desktop engines.** Review explicit pins and application bundles too. Relevant repository locations include `flake.lock`, `hosts/nixos-pablo/home.nix`, `modules/home/pi.nix`, `modules/home/mcp-servers.nix`, `modules/home/dev.nix`, and `packages/default.nix`. Existing working-tree edits must be preserved.
3. **Update running Redis/PostgreSQL images and the container runtime**, preserving database compatibility and state. Verify the version inside the replaced containers; changing a tag in configuration alone does not patch a running container.
4. **Refresh the MCP bridge and other flagged dependencies**, with attention to actual transport/API use. Recheck application bundles and custom runtimes separately from the system executable on PATH.
5. **Review SSH exposure and password authentication** against intended use. This is an exposure-reduction recommendation, not a claim that password authentication is itself a newly disclosed CVE.

No implementation was performed. A later remediation needs explicit build/activation authorization under this repository's rules. Verification should check the booted kernel, running daemon executable, actual browser/runtime versions, trust bundle, and running container versions after changes. Updating source files alone is insufficient.

## Coverage, evidence, and limits

Local evidence came from existing Nix store requisites/derivations, `/proc` executable paths and kernel configuration, generated service configuration, listening sockets, running system/user service lists, Docker version/inspection and version-only commands inside the two running containers, Flatpak inventory, public certificate subjects, and public-registry dependency metadata. No application databases, SSH private keys, credentials, process environments, browser history, or user documents were collected. Only public package names/versions were submitted to OSV.

The installed Flatpak application is Beyond All Reason, with Freedesktop runtime 24.08.37; its full runtime vulnerability set was not independently matched. Additional inventoried components include Python 3.13.13/3.14.4, glibc 2.42-61, systemd 260.1, sudo 1.9.17p2, Tailscale 1.104.1, libvirt 12.4.0, QEMU 11.0.1, and dnsmasq 2.93. Their inclusion in inventory is **not** a clean bill of health.

This is a broad, prioritized assessment, **not an exhaustive enumeration of every current exploit**. It covers all recent KEV additions in the retrieved Oct 21 snapshot, selected current vendor advisories relevant to the observed host, and the specified npm lockfiles. Python environments, Cargo dependencies, all container layers, every Electron bundle, firmware, other project directories, external systems, and VM guests remain outside complete dependency coverage. Source indexes can lag publication, especially on the day of disclosure. Version comparisons can miss downstream patches, and package presence does not prove reachability.

Context Mode tools requested by repository instructions were not exposed in this session. Large inventories were processed in bounded local scripts, returning selected metadata; no Context Mode state or repository automation was created. Existing repository modifications were left intact.
